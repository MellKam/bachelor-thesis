## Language caveats

True of every probe of the language, so not repeated in each cell and not counted against any one feature.

- **TinyGo**: The host must call the exported `_initialize` before any other export (the WASI reactor convention); Go's `init()` and the runtime start there. True of every probe, so it is not a cost on any one feature.
- **Kotlin**: The host must run `_start` (the WASI command convention) before any other export; true of every module that built. Feature 17 (`externref`) is built for the `wasm-js` target, every other probe for `wasm-wasi`.
- **Swift**: Every probe is built freestanding in Embedded Swift (`swiftc -target wasm32-unknown-none-wasm`, linked by the toolchain's `wasm-ld`), the lowest-level route in the 6.4.0 toolchain and the only one that yields a module without WASI imports or a runtime. Embedded mode is itself behind `-enable-experimental-feature Embedded` in 6.4.0 (`swift-frontend -print-supported-features` lists `Embedded`, `Extern` and `BuiltinModule` under "experimental"), so every variant carries `experimental-api`; so do the underscored attributes (`@_expose`, `@_cdecl`, `@_extern`) and the Builtin module. No start call is needed by the host.

- **18 Multiple tables**: Absent (confirmed). No probe; what was checked is in [`probes/18-multiple-tables/kotlin/ABSENT.md`](../probes/18-multiple-tables/kotlin/ABSENT.md). Same root cause as 03/04: no table-emitting code path exists in Kotlin's own codegen at all, so multiple tables is moot.
- **19 Table operations on references**: Absent (confirmed). No probe; what was checked is in [`probes/19-table-operations/kotlin/ABSENT.md`](../probes/19-table-operations/kotlin/ABSENT.md). Same root cause as 03/04/18: table.grow/set/get/size and ref.is_null need a module-owned table, which Kotlin/Wasm's codegen never creates.
- **20 Tail calls**: Absent (confirmed), no return_call. Rests on `mutual-recursion` (fail). Lead: `-Xwasm-enable-tail-calls` ("Emit WebAssembly tail call instructions (return_call / return_call_indirect)") is a real, public compiler flag listed in the compiler's own `-X` help dump, backed by a `WasmTailCallLowering` IR pass, introduced in Kotlin 2.5 (Beta at research time). Needs a build on 2.5+ to verify it lowers mutual recursion specifically (not just self-tailrec) and survives n=1,000,000 before treating this as reached. Checked on the pinned 2.4.21: `kotlinc-wasm -X` lists no tail-call option; `-Xwasm-enable-tail-calls` belongs to 2.5, which was not released at the snapshot date.
- **21 Extended constant expressions**: Absent (confirmed). No probe; what was checked is in [`probes/21-extended-const/kotlin/ABSENT.md`](../probes/21-extended-const/kotlin/ABSENT.md). No evidence of extended-const-expression support found. Non-trivial global initializers always run as code at start-up (`generateField` in `DeclarationGenerator.kt`), consistent with Kotlin/Wasm's reliance on an explicit init routine rather than const-expr globals.
- **22 Typed function references**: Native, a side effect, not requested. Rests on `function-reference` (pass). Function references are GC closures called with `call_ref`. Side effect: the `call_ref` is how a closure's function field is called; the program cannot write or name a typed function reference.
- **23 GC structs and arrays**: Native. Rests on `class-array` (pass). Classes and arrays become GC structs and arrays implicitly.
- **24 GC casts, subtyping, i31, packed fields**: Native, partial: ref.i31 / i31.get not emitted, a side effect, not requested. Rests on `class-hierarchy` (fail). Class subtypes with casts and `ByteArray` as a packed `i8` array; `i31` is not used for a boxed `Int`. Side effect: the subtype declarations and casts come from the class hierarchy, not from anything the program writes as a GC type.
- **25 Multiple memories**: Absent (confirmed). No probe; what was checked is in [`probes/25-multiple-memories/kotlin/ABSENT.md`](../probes/25-multiple-memories/kotlin/ABSENT.md). Confirmed via source: zero references to a second/multiple-memory construct anywhere in the compiler; the single memory is one hardcoded `WasmMemory` object (see 02).
- **26 Relaxed SIMD**: Absent (confirmed). No probe; what was checked is in [`probes/26-relaxed-simd/kotlin/ABSENT.md`](../probes/26-relaxed-simd/kotlin/ABSENT.md). Relaxed SIMD needs base SIMD opcodes, which don't exist in Kotlin's Wasm opcode table at all (see 15/16).
- **27 Exception tags**: Native, tag carries a GC reference. Rests on `try-catch` (pass). Other attempts: `try-catch-new-eh` (pass). `try/catch` compiles to a tag and `try_table`; `-Xwasm-use-new-exception-proposal` selects the encoding.
- **28 Exception handling with exnref**: Native. Rests on `try-catch` (pass). Other attempts: `try-catch-new-eh` (pass). `throw e` inside a `catch` compiles to `try_table` and `throw_ref`; the default and `-Xwasm-use-new-exception-proposal` modules are identical.
- **29 64-bit memory**: Absent (confirmed). No probe; what was checked is in [`probes/29-memory64/kotlin/ABSENT.md`](../probes/29-memory64/kotlin/ABSENT.md). Confirmed via source: no memory64-related code anywhere in the compiler; `WasmLimits`/`WasmMemory` are hardcoded to 32-bit (`UInt`) page counts with no 64-bit variant in the IR model.
- **30 Branch hinting**: Absent (not found). Rests on `internal-likely` (fail). Lead: branch-hint codegen is fully implemented and tested internally — `kotlin.wasm.internal.likely`/`unlikely` lower through `WasmOp.PSEUDO_ANNOTATION_BRANCH_HINT` to a real `metadata.code.branch_hint` section, verified by the compiler's own test `wasm-annotations/branchHint.kt`. But these functions are package-`internal` to the stdlib with no public flag or annotation exposing them to user code (unlike tail calls, 20) — worth watching for a public entry point given how mature the internal implementation already is. Tested (`internal-likely`): `@file:Suppress("INVISIBLE_MEMBER", "INVISIBLE_REFERENCE")` plus `import kotlin.wasm.internal.*` lets user code call `unlikely(...)`, as the compiler's own test does. The 2.4.21 CLI then emits a `metadata.code.branch_hint` section targeting `classify`, but after the code section (order ...,10,0,11,0), and warns that the suppression is UNSPECIFIED and will not be preserved. Pending a decision: it is reached through an internal, undocumented API, so the cell stays 'not found' until it is decided whether such a route counts.

### Swift

- **01 Imports and exports**: Annotation, needs an experimental API, @_extern / @_expose / @_cdecl (underscored attributes), @_extern needs -enable-experimental-feature Extern. Rests on `default` (pass). Other attempts: `expose-only` (fail), `swiftpm-embedded` (pass), `swiftpm-wasip1` (pass). The import is `@_extern(wasm, module:, name:)` and the export `@_expose(wasm, "name")`, but each also needs `@_cdecl` / `@_extern(c)` for a C signature: without them the functions use Swift's calling convention and carry two hidden parameters (`expose-only`). The two `swiftpm-*` variants build the same source through SwiftPM and the official Swift SDK for WebAssembly: the embedded SDK still links wasi-libc (41 KB, WASI imports), the full SDK is a 7.2 MB command module.
- **02 Memory configuration**: Config, needs an experimental API. Rests on `export` (pass), `import` (pass). Limits, stack size and the export or import of the memory are all `wasm-ld` options (`-Xlinker`); Swift has no memory declaration.
- **03 Table and indirect call**: Native, needs an experimental API, implicit table. Rests on `default` (pass). A function pointer is a `@convention(c)` closure. It must live in a mutable global: a `let` is folded into direct calls.
- **04 Table import and export**: Config, partial: table name and limits are fixed (__indirect_function_table, sized to the address-taken functions), needs an experimental API. Rests on `export-table-flag` (fail), `import-table-flag` (fail). `-Xlinker --export-table` / `--import-table`, the same linker behaviour as in C, Rust and Zig.
- **05 Start function**: Absent (confirmed), constructor only. Rests on `init-array` (fail). Other attempts: `static-init` (fail). An `@section(".init_array")` function pointer makes wasm-ld produce `__wasm_call_ctors`, which it then calls at the top of every export, not once; no start section is emitted. Shared upstream limitation of every wasm-ld toolchain in this study (see C, Zig).
- **06 Data segments**: Config, needs an experimental API, --global-base needs a smaller stack. Rests on `global-base` (pass). Other attempts: `default` (pass). `@used` on a global `let` keeps it. The default layout of `swiftc`'s link also puts the first data at 1024 (`default` passes), but that is the linker's default placement, not something the program asks for.
- **07 Custom sections**: Absent (confirmed), bytes land in a data segment. Rests on `section-attribute` (fail). `@section(".custom_section.meta")` (and the bare names `meta`, `custom_section.meta`) puts the bytes in a data segment named after the section, not in a custom section, as `__attribute__((section))` does in C. Swift has no inline or module-level assembly to fall back on. Swift has no inline or module-level assembly. A mixed-language route (a C target in the same package, using the C column's assembly or builtins) is outside what this study counts as Swift exposing the feature.
- **08 Integer operations**: Native, needs an experimental API. Rests on `default` (pass). Rotation has no Swift operator; it is written as masking shifts (`&<<`, `&>>`) that LLVM recognises as `i32.rotl` / `i32.rotr`.
- **09 Float builtins**: Native, needs an experimental API, min/max need the Builtin module. Rests on `builtin-minimum` (pass). Other attempts: `default` (fail). The stdlib has no NaN-propagating min/max. `import Builtin` (behind `-enable-experimental-feature BuiltinModule`) exposes LLVM's intrinsics by name, `Builtin.int_minimum_FPIEEE64` emits `f64.min`.
- **10 Globals**: Absent (confirmed), a Swift global is linear-memory data. Rests on `expose-var` (build failed), `extern-var` (build failed), `extern-var-allow-undefined` (fail). `@_expose(wasm)` is rejected on a variable ("can only be applied to global functions"); `@_extern` on a variable declares a data symbol, so `host.base` is neither imported as a global nor linkable.
- **11 Non-trapping conversions, sign extension**: Native, needs an experimental API. Rests on `plain` (pass). `Int32(x)` traps on NaN and out of range, so the saturating conversion is a hand-written clamp, which LLVM turns into `i32.trunc_sat_f64_s`. Sign extension is `Int32(Int8(truncatingIfNeeded:))`.
- **12 Bulk memory**: Native, needs an experimental API. Rests on `default` (pass). `initializeMemory(repeating:)` and `copyMemory(from:)` of a run-time size lower to `memory.fill` / `memory.copy`; a barrier between them stops the copy of freshly filled bytes from being folded into a second fill (a property of the probe).
- **13 Passive data segments**: Config, partial: memory.init only in the linker-generated initialiser; user code cannot run it, needs an experimental API, needs -Xcc -matomics. Rests on `shared-memory` (fail). `--shared-memory` makes wasm-ld emit a passive segment and copy it from its own initialiser; the program's `load` is an ordinary copy. Same as C and Zig.
- **14 Multi-value**: Absent (confirmed), results returned through an out-pointer. Rests on `struct` (fail), `tuple` (fail), `c-struct-abi` (fail). A tuple or struct result uses Swift's calling convention, which returns it through an indirect (sret) pointer even with the multivalue feature on: `(i32, i32, i32, i32, i32) -> ()`. A tuple cannot be `@_cdecl`. Also tried: a C struct imported through a module map, with clang's experimental multi-value ABI flags (`c-struct-abi`): Swift lowers the result with its own convention, `(i32, i32, i32) -> ()`.
- **15 SIMD**: Native, needs an experimental API, needs -Xcc -msimd128. Rests on `simd-type` (pass). `SIMD4<Int32>`. The operands go through global memory, as in C, Rust and Zig, because LLVM folds `extract(splat + splat)` back to scalar code.
- **16 SIMD memory and bitwise operations**: Native, needs an experimental API, needs -Xcc -msimd128, narrow needs the Builtin module. Rests on `builtin-narrow` (pass). Other attempts: `simd-type` (fail). `SIMD16<UInt8>` loads and stores and the bitwise select compile as written; the clamp-and-truncate narrow does not become `i8x16.narrow_i16x8_s` (`simd-type`). `Builtin.int_wasm_narrow_signed_Vec16xInt8_Vec8xInt16` emits it (`builtin-narrow`).
- **17 `externref`**: Absent (confirmed), compiler crash. Rests on `builtin-ref-null` (build failed). No Swift type maps to `externref`. The only candidate, `Builtin.int_wasm_ref_null_extern`, crashes `swift-frontend` (signal 11). Swift Forums, GSoC 2026 thread on externref support (March 2026): the swiftwasm maintainer says the primitives must first be exposed in Swift before anything else is possible, and the existing example goes through C (`bridge.c`), so nothing is exposed in the released toolchain.
- **18 Multiple tables**: Absent (confirmed), single implicit table. Rests on `two-arrays` (fail). Function pointers from different arrays all share table 0; no Swift construct names another table.
- **19 Table operations on references**: Absent (confirmed), compiler crash. Rests on `builtin-table-size` (build failed). No Swift construct operates on a table. Looking `Builtin.int_wasm_table_size` up crashes `swift-frontend` (signal 11); the intrinsic would need a table symbol Swift cannot declare. The same GSoC 2026 thread lists builtins that store references in a Wasm table only as a stretch goal; nothing is exposed in the released toolchain. A mixed-language route (a C target in the same package, using the C column's assembly or builtins) is outside what this study counts as Swift exposing the feature.
- **20 Tail calls**: Absent (confirmed), opcode in one direction only. Rests on `plain-tail-call` (fail), `tailcallopt` (fail). Swift has no tail-call guarantee or `musttail`. With `-Xcc -mtail-call` the calls in tail position become `return_call` in one direction of the mutual recursion at most, and the probe still overflows the stack. Also tried `-Xllvm -tailcallopt` (`tailcallopt`): no change, `return_call` in one direction and the probe still overflows. Swift has no guaranteed tail call: the 2015-16 evolution proposals (`tail return`, `@tailrec`) were never adopted.
- **21 Extended constant expressions**: Absent (confirmed), no Wasm global. No probe; what was checked is in [`probes/21-extended-const/swift/ABSENT.md`](../probes/21-extended-const/swift/ABSENT.md). Follows from 10; see `ABSENT.md`.
- **22 Typed function references**: Absent (confirmed), function values are table indices. Rests on `function-value` (fail). A function value is an index into the implicit table and is called with `call_indirect`; neither `ref.func` nor `call_ref` can be requested.
- **23 GC structs and arrays**: Absent (confirmed). No probe; what was checked is in [`probes/23-gc-typed-refs/swift/ABSENT.md`](../probes/23-gc-typed-refs/swift/ABSENT.md). Swift's Wasm targets are linear-memory; LLVM has no WasmGC backend to reach (see `ABSENT.md`).
- **24 GC casts, subtyping, i31, packed fields**: Absent (confirmed). No probe; what was checked is in [`probes/24-gc-casts-subtyping/swift/ABSENT.md`](../probes/24-gc-casts-subtyping/swift/ABSENT.md). Follows from 23.
- **25 Multiple memories**: Absent (confirmed), intrinsic takes an index; module invalid. Rests on `builtin-index1` (fail). `Builtin.int_wasm_memory_size_Int32(1)` compiles to `memory.size 1`, but nothing declares a second memory, so the module is invalid.
- **26 Relaxed SIMD**: Native, needs an experimental API, needs -Xcc -msimd128 -Xcc -mrelaxed-simd, intrinsic via the Builtin module. Rests on `builtin-intrinsic` (pass). Other attempts: `fma` (build failed). `addingProduct` is the stdlib's fused multiply-add and lowers to `fmaf`, a libm call that does not link freestanding (`fma`). `Builtin.int_wasm_relaxed_madd_Vec4xFPIEEE32` emits `f32x4.relaxed_madd` directly.
- **27 Exception tags**: Absent (confirmed), errors are return values. Rests on `typed-throws` (fail), `builtin-throw` (build failed). Swift errors travel in the error register: `typed-throws` returns the right value but the module has no tag and no exception instruction. `Builtin.int_wasm_throw` crashes `swift-frontend` (signal 11) at lookup, and a catch would need landingpad IR that Swift never produces. Swift errors are ordinary return values in the error register: no construct asks for a WebAssembly exception.
- **28 Exception handling with exnref**: Absent (confirmed). Rests on `typed-throws` (fail). Re-throwing in Swift is an ordinary `throw` of the error register; nothing becomes `try_table` or `throw_ref`.
- **29 64-bit memory**: Config, needs an experimental API, target wasm64-unknown-none-wasm, -Xlinker -mwasm64. Rests on `wasm64` (pass). The 6.4.0 toolchain ships Embedded Swift stdlib modules for `wasm64-unknown-none-wasm`; no `-Zbuild-std`-style rebuild is needed.
- **30 Branch hinting**: Absent (confirmed). Rests on `slow-path` (fail), `slow-path-llvm-flag` (fail). `_slowPath(x < 0)` (llvm.expect) produces no `metadata.code.branch_hint` section, with or without `-Xllvm -enable-branch-hint`, an option of this toolchain's LLVM 21 that is accepted but changes nothing. Compare C, Rust and Zig. Confirmed as of 2026-10-09: llvm/llvm-project#146230 is still open (last updated 2026-10-01), so no LLVM-based toolchain here can emit the section from source. A hand-encoded `.custom_section.metadata.code.branch_hint` can be written with module-level assembly or a section attribute (shown for Zig), but it names a function index and a byte offset that exist only after code generation, so it patches the output instead of marking a branch in the source; it is not counted as a way to express the feature. Swift has no assembly route at all.
